# Downloads from downloads.planton.ai never retry a throttled or failing answer

**Area**: `pkg/iac/pulumi/pulumibinary/binary.go` (`DownloadBinary`), `pkg/iac/tofu/tofuzip/zip.go` (`DownloadAndExtractZip`), `actions/deploy/action.yml` (its `curl -fsSL` steps)
**Type**: bug (a transient answer fails a deploy)

## What a platform engineer sees

`downloads.planton.ai` is an R2 bucket behind a Cloudflare custom domain. Our zone has no rate-limit rule for it, but the host itself answered HTTP 429 once during a burst of plans from one address; three probes a minute later all answered 200. The Agent Substrate module, which fetches 23 release files per plan, now retries 429 and 5xx with backoff on both engines. The other fetchers still make one plain request, with no retry and no `Retry-After`:

- the CLI's module-binary download (`DownloadBinary`, one `http.Get`, no timeout);
- the OpenTofu module zip download (`DownloadAndExtractZip`, the same);
- the deploy GitHub Action's `curl -fsSL` without `--retry`.

So a CI job or a team running many plans at once fails on a transient 429 or 503 that a retry would ride out.

## What good looks like

- Every fetch from `downloads.planton.ai` retries dropped connections, 429 and 5xx (except 501) a few times with backoff, honoring `Retry-After`.
- A refusal says whether the host is limiting, failing, or does not serve the path.

One shared Go helper fits the two Go sites (the repository already carries `hashicorp/go-retryablehttp` indirectly, whose default policy is exactly this); the action gets `curl --retry 4 --retry-all-errors`.
