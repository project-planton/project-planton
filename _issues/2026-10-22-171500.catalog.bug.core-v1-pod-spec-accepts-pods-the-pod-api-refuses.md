# The core/v1 pod specification accepts pods the Pod API refuses

**Area**: `catalog/kubernetes/core_v1_api.proto` (every kind that embeds the pod: `KubernetesAgentSandbox`, `KubernetesAgentSandboxTemplate`), `catalog/kubernetes/kubernetesagentsandbox/v1alpha1/spec.proto` (`pod_template`'s comment)
**Type**: bug (a refusal that arrives after apply instead of before it)

## What a platform engineer sees

The library adds the Pod API's own checks to the served schema, so a wrong pod is refused before apply. Four checks the Pod API makes are missing. Each one lets a sandbox apply cleanly, and then the controller cannot create its pod: the sandbox stays `Ready=False` and the reason is only in the controller's events.

- **Ephemeral containers in a pod template.** The Pod API refuses `ephemeralContainers` when a pod is created; they are only ever added to a running pod through its `ephemeralcontainers` subresource. `KubernetesCoreV1ApiPodSpec.ephemeral_containers` takes any list.
- **DNS config limits.** The Pod API allows at most 3 `nameservers` and at most 32 `searches`. `KubernetesCoreV1ApiPodDNSConfig` takes any number of either.
- **A value and a source on one environment variable.** The Pod API refuses an `env` entry whose `value` is not empty and that also has a `valueFrom`. `KubernetesCoreV1ApiEnvVar` takes both.
- **Port ranges.** The Pod API requires `containerPort` from 1 to 65535, and `hostPort` from 1 to 65535 when set. `KubernetesCoreV1ApiContainerPort.container_port` is only `required`, and `host_port` takes any number. The curated `WorkloadContainerPort` already carries the range.

One documentation gap sits beside them:

- **When a pod edit applies.** At agent-sandbox v1.0.7 the controller updates only the labels and annotations of a pod that already exists. Every other change to the pod template applies when the pod is next created, for example after a suspend and resume. The sandbox's README, guide and catalog page say so; `pod_template`'s comment, which every generated surface reads, does not.

## What good looks like

- A message or field rule for each of the four checks, in the Pod API's own words, so the CLI, the console and the apply all refuse before the controller does.
- `pod_template`'s comment carries the edit-timing sentence.
- The mirror test still holds the library to the pinned Kubernetes types: these are rules, not new fields.
