# KubernetesAgentSubstrate

**apiVersion**: `kubernetes.planton.dev/v1alpha1`

**Guide**: [GUIDE.md](../GUIDE.md) -- authored operational judgment for this kind: conventions, trade-offs, and what pairs well with it.

**KubernetesAgentSubstrateSpec** installs the Agent Substrate control plane:
the system that runs a large set of mostly idle AI agents ("actors") on a
small set of ready worker pods, suspending an idle actor's memory and disk
into object storage and resuming it on demand, each actor sandboxed (gVisor
or a microVM). One install per cluster serves every product on it.

What it installs, all in `ate-system` unless noted:
  - the API server (`ate-api-server`), the gRPC API a product creates
    atespaces, actor templates, actors and egress policies through, backed by
    PostgreSQL (`database`);
  - the controller (`ate-controller`), which turns each WorkerPool into
    worker pods and registers them with the API server;
  - the node agent (`atelet`, a DaemonSet), which runs actors on worker
    nodes and moves their snapshots to and from object storage (`storage`);
  - the ingress router (`atenet-router`), the data path a request reaches an
    actor by, and the egress gateway (`atenet-egress`), which enforces each
    actor's egress policy and can inject credentials into its outbound calls;
  - the pod-certificate controller (in `podcertificate-controller-system`),
    which signs the certificates every component's mTLS uses, through
    Kubernetes' PodCertificateRequest and ClusterTrustBundle APIs;
  - the three resource definitions (WorkerPool, SandboxConfig,
    CSIDriverConfig) and the default gVisor runtime (SandboxConfig
    `gvisor-default`).
Worker pools, extra runtimes and storage drivers are their own catalog
resources. Atespaces, actor templates, actors and egress policies are records
in Substrate's database, created by the product through the API this kind
outputs, never Kubernetes objects.

CLUSTER REQUIREMENTS: Kubernetes serving the pod-certificate APIs
(certificates.k8s.io PodCertificateRequest and ClusterTrustBundle, with
ClusterTrustBundle projection): GKE 1.36 created with those beta APIs
enabled (they cannot be added later), Kubernetes 1.37 with the feature
gates, or a kind cluster configured as upstream's own. A CNI that enforces
NetworkPolicy, because the install's isolation is a default-deny policy.
Upstream supports GKE and kind.

DISTRIBUTION AND VERSION: Agent Substrate publishes no images and no
installable release, so Planton publishes both: upstream's v0.5.0 built by
upstream's own publisher, every image digest-pinned, at
https://downloads.planton.ai/releases/agent-substrate/v0.5.0/. The modules
compose that tree the way upstream's installer does and apply the typed
settings below onto it. There is NO version field: the catalog's Substrate
resource kinds mirror these resource definitions field for field, and each
Substrate release is a deliberate catalog update. Before 1.0 every minor
release is a reinstall upstream (its database schema migrates irreversibly),
so the kind refuses an apply over an older minor's installation or database,
and says how to move across.

GENERATED SECRETS: the certificate authorities behind every component's
mTLS, the actor-identity CA, the egress interception CA and the actor token
signing key are generated by the modules in upstream's exact format and
kept in the deployment's state. A re-apply never replaces them; a destroy
does, exactly like an upstream reinstall.

NAMESPACE IS FIXED: `ate-system` is baked into upstream's manifests, the
API's server name and its token audience. Who owns it is still a choice
(`namespace`, `create_namespace`): Secrets this kind reads (S3 credentials,
external database connection strings) must be in it before the deploy.

Built for 100% parity with every setting upstream's installer and its
components offer; the guide accounts for each one.

## Validation Rules

- `gcs_needs_gke`: storage.gcs authenticates keylessly through GKE Workload Identity, so it needs platform.gke; on another cluster use storage.s3
- `cloud_sql_needs_gke`: database.cloud_sql connects through the Cloud SQL Auth Proxy with GKE Workload Identity, so it needs platform.gke
- `cloud_sql_iam_needs_api_server_identity`: database.cloud_sql logs in as the API server's Google service account, so set platform.gke.api_server_service_account (or turn cloud_sql.iam_authentication off and give a connection string)
- `extproc_needs_envoy`: egress.additional_ext_proc_service splices a filter into Envoy's configuration, so it needs router.dataplane envoy
